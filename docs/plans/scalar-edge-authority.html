§1 — One architectural pattern, twenty-four instances

A standard name's state is stored twice: once as a relationship, which is authoritative, and once as a scalar cached on the node. The scalar is what gates the work — the export reads it, the lifecycle branches on it, the review pool selects on it — so when the two disagree, the stale copy wins over the authoritative edge.

Seven separate defects were found on 2026-09-08 before anyone named the mechanism: a rename emptied source_paths while the PRODUCED_NAME edge stood; 27 names read docs_stage='accepted' with no winning docs review; 538 asserted validation_status='valid' with no validated_at; 2,096 carried a false origin; 328 asserted link_status='resolved' against an absent target. Each was repaired individually. They are one pattern with seven symptoms, and a review of the whole surface found twenty-four mirrored pairs, not seven.

§2 — Why the order matters more than the change

Deriving first would destroy data. Two measurements make this concrete and they are the reason this plan exists as its own document rather than as a repair node.

REFERENCES is not a declared relationship type in the graph — there are zero such edges — while 2,948 standard names carry a non-empty links scalar. So a migration that executes the DERIVE verdict for links today would read an empty relationship set and blank the links on 2,948 names. The scalar is currently the only copy. Its 6,682 edges must be materialised from the scalar first, verified count-for-count, and only then may the scalar be derived from them.

The same trap in a second form: 100 StandardNameSource rows carry more than one target edge among 117 divergences on the produced-name mirror. Removing produced_sn_id before adjudicating those 100 discards the only record of which target was intended.

So every pair follows the same three beats, and a node may not skip to the third:

  1. Materialise the relationship from the scalar where the relationship does not yet exist, and prove the count matches.
  2. Adjudicate every row where scalar and relationship disagree, or where the relationship is ambiguous, before either is treated as authority.
  3. Derive the scalar from the relationship, or give it a single named writer, per the review's verdict.

§2a — The census figures are a prior reading, not an authority, and 127 targets are absent

Measured live 2026-09-09 while materialising the first pair: the population is 2,949 non-empty links scalars and 6,684 entries, not the 2,948 and 6,682 §1 records. Nothing drifted mysteriously — the difference is this repository's own work on the same day, one restored identity and forty relabelled origins. The lesson is procedural and it cost a node: a figure measured on one date must not be written into a gate as a required equality. Measure the cohort at run time, record what was measured with its timestamp, and read §1's table as the prior reading it is.

The substantive finding is larger than the drift. Of the 6,684 link entries, 6,557 resolve and 127 name a target id with no StandardName node at all. So an all-or-none materialisation of this pair is impossible today, and the plan's own §2 wording is what resolves it: the edges are materialised first and verified count-for-count, and only then may the scalar be derived. Count-for-count parity is a precondition for the DERIVE beat, not for the materialise beat.

So the first pair materialises its 6,557 resolvable edges and carries the 127 as a named exclusion ledger — one row each with the source name, the absent target id and the cause. This is not the partial-closure failure the archive restore correctly refused an hour earlier, and the distinction is worth keeping because the two look alike: a partial archive closure asserts a restored identity carrying a fraction of its evidence, which is a false claim about a thing. Materialising every resolvable edge asserts nothing false — each edge that exists is correct, the scalar remains the only record of the 127, and the ledger names them. Nothing is destroyed and nothing is over-claimed.

The DERIVE beat for this pair stays shut until parity reaches 6,684. The 127 are expected to shrink without separate adjudication: several are likely among the identities the deletion-recovery plan is still restoring, so a later re-materialisation picks them up. They are named and left, not chased.

§3 — Sequence, one pair per node, largest exposure first

One pair per node. Each node states which of the three beats it performs, and a node that performs beat three cites the node that completed beats one and two for that pair. Ordering is by publishable exposure, because a divergence that touches no publishable name is a hygiene item and one touching 1,985 is a correctness risk in every release until it closes.

The five KEEP AS DISTINCT boundaries are deliverables of this plan too: each retires a supposed defect, and recording why two values legitimately differ prevents the next census from reporting it as damage. A plan that only fixes things leaves that knowledge nowhere.

§4 — What closing this prevents

Every defect this pattern produced was found by accident, one at a time, by someone looking at something else. The rename that emptied source_paths was caught only because the export refused an unsourced name; the 27 names claiming an accepted docs stage were caught by a census aimed elsewhere; the 538 undated validations were caught while investigating a quarantine. Each cost a day and each repair was correct and local.

The measure of this plan is not repaired rows. It is that a repeat census after a later export, a later import and a later pipeline run returns the same numbers — because the scalar can no longer drift from the edge that defines it.

§ Decisions

May a DERIVE node run before its pair's relationship is materialised and count-verified?

<p><strong>Never.</strong> A DERIVE node may not run before its pair's relationship set is materialised and count-verified, and the reader inventory turns that from a prudent default into a measured requirement.</p><p>The inventory's first finding is that <em>no current reader resolves a relationship in place of its scalar</em> — every publication and pipeline gate still reads the stored value — so nothing today can observe a partial set, because nothing reads the set at all. That is precisely why the risk arrives with the replacement readers rather than before them, and it is marked as a static finding rather than a claim about live transaction isolation.</p><p>What the replacements would do on a partial set is named per reader, and every one is an admission or publication decision: <code>export.py:984</code> would return only committed <code>REFERENCES</code> targets, <code>graph_ops.py:12309</code> could see several <code>PRODUCED_NAME</code> targets, <code>graph_ops.py:17122</code> would undercount docs revisions, <code>graph_ops.py:16477</code> would undercount refinement depth, and <code>review/pipeline.py:351</code> would see no selected review until its edge exists. The repository text does not prove an all-pair transaction boundary, so the interleaving is <strong>unverified from source</strong> and must not be assumed.</p><p>A live instance settles it. On 2026-09-09 all 31 WEST rows withheld from a catalog cut held intact documentation and 285 intact docs-axis review edges while two mirrored scalars read pending and null — a recoverable regression. Had a DERIVE pass run against a partially materialised review set, it would have written that emptiness into the scalar and made the regression permanent. Same shape as this section's <code>REFERENCES</code> trap, where 2,948 names would lose their links to an empty read.</p>

After a scalar is derived from its relationship, is the stored copy removed or kept as a read cache?

<p><strong>Remove.</strong> The reader inventory recommends removal for all twelve DERIVE surfaces, and its reason for rejecting <code>keep-as-cache</code> is stated as an absence rather than a refutation, which is the honest form: <em>no repository source reports query timing or cost for any of the twelve</em>, so there is no evidence for a cache anywhere. A cache justified by an unmeasured performance worry would reintroduce this plan's whole failure mode to buy something nobody has shown is needed.</p><p><strong>The non-cheap rows are sequence blockers, not cache candidates</strong> — the distinction that makes this decision safe to lock now. <code>links</code> waits on full <code>REFERENCES</code> parity, <code>produced_sn_id</code> on multi-target adjudication, the axis reviewer projections on an atomic selected-review write, and <code>origin</code> on separating one value that carries incompatible meanings. Each names a prerequisite, none names a reason to retain a copy. Cheap removals, whose replacements are cardinality-one or one-hop reads: <code>primary_cluster_id</code>, <code>dd_path</code>/<code>signal</code>, <code>deprecates</code>/<code>superseded_by</code>, and the review timestamps once one shared authority predicate exists.</p><p><strong>The measured cost of keeping a copy is now on the record.</strong> On 2026-09-09, 37 names were dropped from a WEST catalog cut on the strength of two stale scalars while the evidence they mirror sat undamaged — 31 of 31 rows with documentation intact, 285 docs-axis review edges intact, best scores 0.9375 to 1.0. A <code>docs_stage</code> resolved from those edges at read time could not have regressed, because there would be no second copy to fall out of step, and the writer that caused it was ordinary concurrent restore work rather than anything exotic.</p><p><strong>The reopening condition, stated so it is not a loophole:</strong> if profiling later proves a material relationship-query cost, the retained value must have exactly one named writer and an edge-to-scalar reconcile. That makes it a cache with an owner, which is a different decision from a DERIVE scalar with none — and it must be argued on measured numbers, never on the expectation of them.</p>

§ Followups

Materialise the REFERENCES edges before deriving anything, or 2,948 names lose their links

The first node materialises and verifies; it derives nothing. There are zero REFERENCES edges in the graph and 2,948 standard names carry a non-empty links scalar, so the scalar is currently the only copy of that information. A node that executes the DERIVE verdict first reads an empty relationship set and blanks all 2,948. Build the 6,682 edges from the scalar, prove the count matches per name, and stop there.

The second trap has the same shape. 100 StandardNameSource rows carry more than one target edge, among 117 divergences on the produced-name mirror. Adjudicate those 100 before produced_sn_id is removed anywhere, because the scalar is the only record of which target was intended.

One pair per node, three beats, in order: materialise, adjudicate, derive. A node performing the third beat must cite the node that completed the first two for that pair. Order the pairs by publishable exposure — links at 1,985 first, then source_types at 1,750, docs_chain_length at 1,181 — because a divergence touching no publishable name is hygiene and one touching 1,985 is a correctness risk in every release until it closes.

The five KEEP AS DISTINCT boundaries are deliverables too: each retires a supposed defect, and recording why two values legitimately differ is what stops the next census reporting it as damage.
