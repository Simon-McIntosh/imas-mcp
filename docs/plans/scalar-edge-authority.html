§1 — One architectural pattern, twenty-four instances

A standard name's state is stored twice: once as a relationship, which is authoritative, and once as a scalar cached on the node. The scalar is what gates the work — the export reads it, the lifecycle branches on it, the review pool selects on it — so when the two disagree, the stale copy wins over the authoritative edge.

Seven separate defects were found on 2026-09-08 before anyone named the mechanism: a rename emptied source_paths while the PRODUCED_NAME edge stood; 27 names read docs_stage='accepted' with no winning docs review; 538 asserted validation_status='valid' with no validated_at; 2,096 carried a false origin; 328 asserted link_status='resolved' against an absent target. Each was repaired individually. They are one pattern with seven symptoms, and a review of the whole surface found twenty-four mirrored pairs, not seven.

§2 — Why the order matters more than the change

Deriving first would destroy data. Two measurements make this concrete and they are the reason this plan exists as its own document rather than as a repair node.

REFERENCES is not a declared relationship type in the graph — there are zero such edges — while 2,948 standard names carry a non-empty links scalar. So a migration that executes the DERIVE verdict for links today would read an empty relationship set and blank the links on 2,948 names. The scalar is currently the only copy. Its 6,682 edges must be materialised from the scalar first, verified count-for-count, and only then may the scalar be derived from them.

The same trap in a second form: 100 StandardNameSource rows carry more than one target edge among 117 divergences on the produced-name mirror. Removing produced_sn_id before adjudicating those 100 discards the only record of which target was intended.

So every pair follows the same three beats, and a node may not skip to the third:

  1. Materialise the relationship from the scalar where the relationship does not yet exist, and prove the count matches.
  2. Adjudicate every row where scalar and relationship disagree, or where the relationship is ambiguous, before either is treated as authority.
  3. Derive the scalar from the relationship, or give it a single named writer, per the review's verdict.

§3 — Sequence, one pair per node, largest exposure first

One pair per node. Each node states which of the three beats it performs, and a node that performs beat three cites the node that completed beats one and two for that pair. Ordering is by publishable exposure, because a divergence that touches no publishable name is a hygiene item and one touching 1,985 is a correctness risk in every release until it closes.

The five KEEP AS DISTINCT boundaries are deliverables of this plan too: each retires a supposed defect, and recording why two values legitimately differ prevents the next census from reporting it as damage. A plan that only fixes things leaves that knowledge nowhere.

§4 — What closing this prevents

Every defect this pattern produced was found by accident, one at a time, by someone looking at something else. The rename that emptied source_paths was caught only because the export refused an unsourced name; the 27 names claiming an accepted docs stage were caught by a census aimed elsewhere; the 538 undated validations were caught while investigating a quarantine. Each cost a day and each repair was correct and local.

The measure of this plan is not repaired rows. It is that a repeat census after a later export, a later import and a later pipeline run returns the same numbers — because the scalar can no longer drift from the edge that defines it.

§ Decisions

May a DERIVE node run before its pair's relationship is materialised and count-verified?

Recommendation: never. The links pair shows why in one measurement — zero REFERENCES edges against 2,948 populated scalars, so deriving first is data loss rather than a migration. Making it an invariant costs nothing where the relationship already exists and prevents the one irreversible mistake this plan can make.

After a scalar is derived from its relationship, is the stored copy removed or kept as a read cache?

Recommendation: remove it where a query can read the relationship directly, and keep it only where a measured query cost forces the cache — in which case it becomes a KEEP AND RECONCILE pair with a named single writer, not a DERIVE. A cache with two writers is the defect this plan closes, so a retained scalar needs its writer named in the same commit that retains it.

§ Followups

Materialise the REFERENCES edges before deriving anything, or 2,948 names lose their links

The first node materialises and verifies; it derives nothing. There are zero REFERENCES edges in the graph and 2,948 standard names carry a non-empty links scalar, so the scalar is currently the only copy of that information. A node that executes the DERIVE verdict first reads an empty relationship set and blanks all 2,948. Build the 6,682 edges from the scalar, prove the count matches per name, and stop there.

The second trap has the same shape. 100 StandardNameSource rows carry more than one target edge, among 117 divergences on the produced-name mirror. Adjudicate those 100 before produced_sn_id is removed anywhere, because the scalar is the only record of which target was intended.
